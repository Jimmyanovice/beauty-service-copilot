# 技术方案

## 应用

Flask负责页面和API，Socket.IO推送更新。本地Qwen3:8b通过Ollama兼容接口生成JSON建议，SQLite保存分析、审核和人工任务。数据使用赛题虚构聊天、结构化订单及工单，默认词法检索和进程内缓存。

## 工作流

| 节点 | 作用 |
| --- | --- |
| Evidence | 按会话和买家消息确定服务时点，关联合法业务证据 |
| Safety | 识别并先保存风险任务，模型排队不会推迟登记 |
| Draft | 证据/知识检查、限用证据路径或模型生成，以及文本声明校验 |
| Verify | 关联证据、时点警示和必要的人工复核任务 |
| Audit | 保存结果、原稿/修正、执行记录和实际用量 |

实现：`src/orchestration/workbench_workflow.py`及 `src/agents/assist_agent.py`。

人工编辑、采纳、拒绝和任务状态更新由应用单独保存。没有自动发送消息、改订单或执行商家售后，也未使用LangGraph的interrupt或持久化checkpoint。

## 智能分析与约束

明确诉求由轻量规则识别，模糊意图可由同次生成补判。基础情绪与场景标签分开，风险下限不能由模型降低。

JSON Schema和Pydantic约束输出结构，有限的业务规则核对金额、状态、来源、时点、执行承诺及未核实原因。原稿和修改保存，规则有效仍需要人工语义审核。

## 性能成本

紧凑字段、360 Token输出上限、按版本/模型配置隔离的精确缓存和有界队列减少重复请求。仅无风险且明确的问候、单订单既往发货/运单查询可以走证据路径。

规则路径不代替混合问题、风险或历史争议的分析；相似咨询不一定具有相同订单事实，当前不使用语义缓存。

## 数据与身份

快照不能当成历史状态。历史回放排除未来记录，缺历史状态时明确未知。昵称只提供跨会话关联候选，人工填写依据后才合并轨迹。

上传包的字段清理、匿名昵称和公开授权边界见 `DATA_POLICY.md`。数据库在运行时生成，初始没有原开发环境的人工数据。
